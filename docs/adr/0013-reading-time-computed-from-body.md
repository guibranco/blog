# Reading time is computed at build time from the post body; the front matter field is an optional override

`reading_time` was a mandatory front matter field, typed by hand when a Post was written and never revisited. It drifted: every edit that added or cut a section left the number where it was, and a spot check across the 60 existing posts found values off by a factor of two in both directions (a 10,700-word Trip declared 22 minutes; a 640-word note declared 2). It also added friction with no editorial value — nobody chooses a reading time, they estimate one — and `audit_blog.py` warned whenever it was missing, so the estimate had to be made before a post could pass CI.

**`_plugins/reading_time.rb` fills `reading_time` on every post whose front matter does not set it.** It is a Jekyll Generator, so it runs before anything renders and the value is already in `post.data` when the post page, the post cards, the home's featured block and `search.json` read `reading_time` — none of those templates changed. It counts the words of the *source* body (Markdown plus the inline HTML the posts use for callouts and tables) rather than the rendered HTML: a Generator has no rendered output yet, and a `:post_render` hook would run too late for listings that render before the post. Counting rules: fenced code blocks and `<pre>` blocks are counted separately at a slower rate, since readers scan code rather than read it; HTML tags, comments, `<script>`/`<style>`, Liquid tags and objects, and entities are markup, not words; Markdown links and images keep their text and drop the URL; each image (Markdown, `<img>`, or a `photo.html` include) adds a fixed number of seconds so a Gallery-heavy Trip is not a two-minute read. The result is rounded up and never below one minute.

**The rates are calibrated against the hand-authored values, not taken from a blog post.** Prose at 200 words per minute, code at 150, ten seconds per image. Across the 60 posts the median ratio of computed to hand-authored is exactly 1.0 at 200 wpm, and 150 wpm for code is the rate at which the four code-heavy deploy guides land within a minute of what the author had typed; the alternatives (excluding code entirely, or counting it at half speed) were each two to five minutes off on those posts. The rates are overridable in `_config.yml` under a `reading_time:` block (`words_per_minute`, `code_words_per_minute`, `seconds_per_image`) so a recalibration is a config change, not a code change. pt-BR and en posts use the same rate: the corpus is too small to fit two, and the hand-authored values showed no per-language pattern.

**A manual `reading_time:` still wins, and the audit warns when it has drifted.** The field stays in the front matter reference as an override for the rare post where the estimate is wrong (a post that is mostly a table, say). `audit_blog.py` no longer requires it; instead, when a post carries one, the script computes the same estimate and warns when the two differ by more than 10% *and* more than one minute — the one-minute floor keeps rounding on short posts from tripping it. The warning is not blocking: an override is a legitimate editorial call, and the audit's job is to make the drift visible, not to forbid it. A non-integer or non-positive value is also a warning.

**One algorithm, two implementations, kept in lockstep.** The build runs Ruby; the CI scripts run Python without a Jekyll installation. `.github/scripts/reading_time.py` is a line-for-line port of the plugin (same stripping order, same word regex, same defaults, and it reads the same `_config.yml` block) and is verified to produce identical prose/code/image counts on every existing post. `audit_blog.py` uses it for the drift check and `build_og_cards.py` uses it so the generated Open Graph card shows the same number as the page for a post that no longer carries the field. Both files say so in their headers; a change to one is a change to both. A shared implementation was not an option — there is no runtime the Ruby build and the Python scripts have in common — and dropping the Python side would have meant either no drift check or a card without a reading time.

## Consequences

- New posts omit `reading_time`. The README's post recipe and front matter reference say so; `git_last_modified.rb`'s "front-matter-only edits are not updates" rule (ADR-0007) is unaffected, and removing the field from an existing post is such an edit.
- The 60 existing posts kept their hand-authored values when the plugin merged (the override path), so nothing visible changed then. The field was removed from all of them in one follow-up sweep, so every post now shows the computed value; the audit's drift warning remains for any override added later.
- Word counts are made on the source, so the Liquid output of an include (a photo caption, a series box) is not counted; the include's own parameters are stripped as Liquid. This slightly undercounts captions and is accepted — the alternative, rendering every post before counting, would move the plugin to a render hook and reintroduce the ordering problem above.
- The counts are not localized: pt-BR and en share the rates. Revisit if the corpus grows enough to show a real per-language difference; the config block already exists for it.
