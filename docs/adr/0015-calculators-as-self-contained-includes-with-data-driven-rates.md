# A Calculator is one self-contained include; its rates live in `_data/calculators/` and its tables render without JavaScript

The blog quotes concrete numbers about Irish tax, Dublin rents and Brazilian CLT pay, but only as static tables inside prose. Readers come back to and link to something they can type their own numbers into, and nothing on the site could do that: posts are Markdown with a small set of inline-HTML components (callouts, compare tables, cards), the layout loads exactly the scripts every post needs, and the only optional script is the lightbox behind `gallery: true`. Adding a `<script>` to a post body was never done, and would have put logic and tax figures — which change every year — in the middle of a published article.

**A Calculator is a single Liquid include under `_includes/calculators/`, and it carries everything it needs.** `{% include calculators/net-salary-ie-br.html %}` is the whole integration; the include holds its markup, a `<style>` block scoped under its own class and written against the tokens in `main.css` (so it follows the dark theme for free), and a vanilla-JavaScript IIFE. Nothing is added to the post layout, `main.css` or `assets/js/`: the cost of a Calculator is paid only on the pages that embed it, and a Calculator can be deleted by deleting one file. The script guards itself with a `data-calc-init` marker and builds its output with `createElement`, never with HTML in strings — kramdown finds the end of a raw HTML block by counting tags, and a `</div>` inside a JavaScript string would close the block early. For the same reason the include emits no blank line anywhere in its output (a blank line ends a kramdown HTML block too), which is why its Liquid tags use `{%- -%}` throughout.

**Every number lives in `_data/calculators/<name>.yml`, next to the year and the sources it was checked against.** Bands, rates, credits, thresholds and the default exchange rate are data; the script only knows the *shape* of a progressive band table or a bracket table, not any figure. The same file carries `tax_year`, `updated`, a `sources` list (URL, what it covers, the date it was verified against the official table) and the UI copy per Post language. Updating for a new tax year is a data edit that touches no logic, and a reviewer can check the file against Revenue or the Receita Federal without reading JavaScript. Copy lives in the data file rather than `_data/i18n.yml` because it belongs to one Calculator, not to the site chrome, and because a Calculator is Post content: it is written in the Post language (ADR-0006) and does not switch with the UI language toggle.

**The include renders the rate tables server-side, so the page degrades to the tables the calculator would have used.** The `<details>` block of assumptions is plain Liquid over the data file — every band, credit, threshold and source, formatted by the new `money` and `percent` filters in `_plugins/money.rb` (Liquid has no number formatting) — and the form starts `hidden` until the script removes the attribute. With JavaScript off a reader sees the title, a one-line note, the full tables and the sources; nothing interactive is half-rendered. The same data reaches the script as a JSON `<script>` block, so the fallback tables and the live calculation can never disagree.

**The first Calculator compares net salary in Ireland and Brazil for tax year 2026, and models the payslip rather than an average rate.** Ireland: PAYE on gross less the relievable pension contribution (age-related limit, €115,000 earnings cap, relief on income tax only), tax credits by status, USC on the full gross with the €13,000 exemption, PRSI Class A with the €352 weekly threshold, the tapered €12 credit and the mid-year rate change blended by days. Brazil: INSS progressive to the ceiling, IRRF on gross less the larger of the legal deductions (INSS plus dependants) or the simplified discount, then the Lei 15.270/2025 reduction on the month's gross taxable income; the year is eleven regular months, the holiday month with its third taxed together, and the 13º taxed on its own — the reduction applies to it too. FGTS is shown as a separate line and never inside net pay, because it is deposited, not paid.

## Consequences

- Both nets show in both currencies at the rate typed into the form; the data file's rate is only a dated default.
- A Calculator's `<style>` and `<script>` are repeated if it is embedded twice on one page; the `id` parameter keeps the form ids unique, and the init guard keeps the script from running twice. Two copies of a Calculator on one page is not a case worth optimizing for.
- `audit_blog.py` does not validate `_data/calculators/`; a wrong figure fails no build. The `sources[].verified` dates are the audit trail, and the `updated` stamp is printed on the page so a stale year is visible to readers.
- The Post language decides the copy; a Calculator embedded in an `en` Post shows English labels and `en-IE` number formatting, in a `pt-BR` Post Portuguese labels and `pt-BR` formatting. Adding a third Post language means adding a `labels` block per Calculator.
- Rates that change mid-year are modelled as dated periods (PRSI in 2026); anything else is assumed constant for the tax year. Tax back, benefits in kind, bonuses, health insurance, meal vouchers and individual deductions are out of scope and the page says so.
- See [`CONTEXT.md`](../../CONTEXT.md)'s new **Calculator** term. Follow-up Calculators (cost of living, a per-post currency converter) reuse the same layout: one include, one data file, tables rendered as the fallback.
