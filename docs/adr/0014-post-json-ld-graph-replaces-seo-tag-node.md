# A post's structured data is one JSON-LD `@graph` from `schema.html`; jekyll-seo-tag's node is switched off on posts

Before this decision a post page carried three `<script type="application/ld+json">` blocks from two sources: a `BlogPosting` written by `jekyll-seo-tag` (which emits one on every page, unconditionally), and an `Article` plus a `BreadcrumbList` written by `_includes/schema.html`. The `BlogPosting` and the `Article` described the same post under two `@type`s with partly different data (only the gem's had `dateModified` and `mainEntityOfPage`; only ours had a `publisher`), which the Rich Results Test and the Schema Markup Validator report as two article entities on one page. The include also HTML-escaped its strings (`escape`), so a title with `&` reached the JSON as the literal text `&amp;` — entities are not decoded inside a `<script>`.

**`_includes/schema.html` now emits everything a post page says about itself, as one `@graph`.** `Article` (with `mainEntityOfPage`, `url`, `inLanguage` from the mandatory `lang` field — [ADR-0006](0006-post-language-mandatory-no-site-default.md) — `dateModified` from the `last_modified_at` that `git_last_modified.rb` computes — [ADR-0007](0007-git-diff-based-last-modified-date.md) — falling back to `datePublished`, `keywords` from the Tags and `articleSection` from the Categories), `BreadcrumbList`, and, when the post warrants them, the Series `ItemList` and a `FAQPage`. One graph rather than several scripts because the nodes reference one page and one author, and because a single place is easier to keep free of the duplicate the validators had been flagging. Free text goes through a new `json_ld_string` filter (`_plugins/schema_filters.rb`): a JSON string literal with `</` escaped, so no title, description or answer can close the `<script>` early — the reason `jsonify` alone was not enough for text an author writes.

**The gem's JSON-LD is switched off on posts with a flag, not by dropping the gem.** `{% seo %}` still renders every Open Graph, Twitter Card and canonical tag the post needs, and re-implementing those by hand would be more template to maintain than the node we want gone. jekyll-seo-tag 2.9 has no option to omit the script, so `_plugins/seo_tag_json_ld_opt_out.rb` adds one in the gem's own idiom — `{% seo json_ld=false %}`, next to its `title=false` and `canonical=false` — by wrapping the `<script>` in the gem's template in an `{% if seo_tag.json_ld? %}` when the template text is read. Only the post layout passes the flag; the home, category, tag and series pages keep the gem's `WebSite`/`WebPage` node, which does not conflict with anything those pages emit. The plugin raises at build time if a gem upgrade changes the template so the block is no longer found: silently going back to two article nodes is the regression it exists to prevent, and a loud failure is preferable to a quiet one.

**Series parts are an `ItemList` ordered by `series_part`, emitted from one include in two places.** `_includes/schema-series.html` renders the node for a Series slug — `ListItem`s whose `position` is the part number, `itemListOrder` ascending, `numberOfItems` — and is used both inside a part's `@graph` (next to the series banner) and on `/series/`, where `series.html` emits one such node per Series; the two places therefore can never drift. The part's `Article` also gets `position` (its `series_part`) and `isPartOf` a `CreativeWorkSeries` named after `series_title`, which is the type `isPartOf` expects (an `ItemList` is not a `CreativeWork`, so it cannot be the value there).

**A Trip's points become `TouristDestination`s with coordinates; its Countries become `about`.** The same `locations`-then-`location` merge as `post-map.html` feeds `contentLocation`, each point carrying `GeoCoordinates` from `lat`/`lng` and, where it can be resolved, `containedInPlace` → `Country`. The Country of a point is read from the last comma-separated segment of its label, matched against the post's `countries` by English `name` or pt-BR `name_pt` from `_data/countries.yml` ([ADR-0010](0010-country-identified-by-english-name.md)) — labels are written as "Sliema, Malta" or "Bologna, Itália" — with the post's only Country as the fallback when the label ends in something else ("Blue Lagoon, Comino"); a multi-Country Trip whose label matches nothing simply omits the containment rather than guessing. The Countries themselves are emitted as `about` so a Trip is tied to its Country even when no point resolves. `TouristDestination` was chosen over plain `Place` because a Trip is, by the glossary's definition, a travel post; the type has no required properties, so it costs nothing where a point is a concert venue rather than a beach.

**The `FAQPage` is read from the rendered body, and only on posts that opt in.** Google's FAQ guidelines require every listed question and answer to be visible on the page, so a hand-written list in the front matter — which would drift from the text the same way `reading_time` did ([ADR-0013](0013-reading-time-computed-from-body.md)) — was rejected. With `faq: true`, the `faq_items` filter takes every `h2`–`h4` whose text ends in `?` as a `Question`, and the text up to the next heading of the same or a higher level as its `Answer`, dropping code blocks, tables, figures and scripts and flattening the rest to plain text. A heading that is not a question produces no entry of its own, so a post can mix ordinary sections with a Q&A one; a lower-level heading nested under a question (an `h3` under an `h2`) does not end that answer, so its content stays in the parent's answer. A question left with no prose once those blocks are dropped is omitted. It is opt-in because a heading phrased as a question is common in posts that are not FAQs (a deploy guide with a "Why two instances?" section), and marking those up would misrepresent the page. The one post flagged at the time of this decision is "Quanto cobrar?", whose six sections are all questions with answers.

**The author is a `Person` with `sameAs`.** The profile URLs already in `_config.yml`'s `social:` block feed `sameAs` — all of them except `website` (that is the Person's `url`) and `whatsapp` (a chat deep link, not a profile). The list of keys lives in the include, so adding a network to `social:` is a one-line change there.

## Consequences

- Category, tag and series pages do not include `schema.html` and still carry the gem's `WebPage` node only; a `BreadcrumbList` there is a separate change (the include already resolves `page.subcategory` for it).
- Whether the Rich Results Test and the Schema Markup Validator accept the output is checked on live URLs after deploy, one standard post, one Series part and one Trip at least. Before merging, the built site was checked offline for JSON validity of every block, one node per `@type` per page, and every `@type`/property against the schema.org vocabulary (including which types each property is allowed on); nothing in CI repeats that check.
- Since 2023 Google shows FAQ rich results only for well-known government and health sites; the `FAQPage` node is still valid structured data and costs nothing, but it should not be expected to change how a post appears in results.
- A question heading whose answer is only a code block or a table produces no `Question` (there is no prose to quote); write one sentence of answer before the code if it should appear.
- Upgrading `jekyll-seo-tag` may fail the build if the template's `<script>` changes; the fix is to adjust `JSON_LD_SCRIPT` in the plugin, or, if the gem grows its own opt-out, delete the plugin and use that.
- See [`CONTEXT.md`](../../CONTEXT.md)'s new **FAQ** term.
