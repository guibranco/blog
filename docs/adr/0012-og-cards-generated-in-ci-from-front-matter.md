# Open Graph cards are rendered in CI from the front matter and committed to the PR branch

Every Post needs a 1200×630 raster for og:image / twitter:image (`image:`). A Trip has a photo that serves as both Hero and social image. An illustrated Post did not: it needed a hand-designed SVG Hero *and* a hand-rasterized PNG — CairoSVG on a machine with Playfair Display, Source Serif 4 and JetBrains Mono installed, or the typography silently fell back to Georgia and the card no longer looked like the site. ADR-0002 already lists the PNG as the one thing a Claude-authored post could not finish on its own ("rendered externally … added in a follow-up commit"). It was the most manual step in publishing.

**`.github/scripts/build_og_cards.py` renders the card, and `og-cards.yml` runs it on every PR that touches `_posts/`.** For each changed Post that is not a Trip (`location`/`locations`/`countries`) and whose `image:` is not already a real raster:

- with no `cover:` and no `image:`, a **templated card** is rendered from the front matter — title (split at the first `: `/spaced dash into a headline and an italic/green kicker, the way the hand-made cards do), description, first Category + Subcategory as the eyebrow, Series and part, date, reading time, and Tags as chips on the dark style;
- with a `cover:` SVG and no `image:`, that **hand-authored SVG is rasterized as-is** (uniform scale, letterboxed on its own background colour) — the follow-up commit ADR-0002 described now happens in CI;
- the result lands at `assets/img/posts/<post-slug>.png`, `image:` is written into the front matter, and both are committed to the PR branch with a PR comment, mirroring `sync-category-tag-data.yml`. Because the post layout falls back to `image` when there is no `cover`, the generated card is also the on-page Hero, so a new non-travel post ships with no image work at all.

**Two templates, chosen by Category.** The repo's hand-made covers fall into two families: *cream editorial* (`#f5f0e8` ground, inset frame, mono eyebrow in `#b85c00`, Playfair Display 400 headline in `#1a1714` with an italic `#2d6a4f` second thought, Source Serif 4 standfirst) and *dark tech* (`#0f0e0c` ground, faint grid, green glow, `// eyebrow` in `#93c97a`, Playfair Display 700 headline in `#f5f0e8` with a `#93c97a` kicker, `#e8a33d` rule, mono tag chips). Coding and Infrastructure posts get dark; everything else gets cream; `card_style: dark|cream` in the front matter overrides. Line-wrapping and font stepping are computed by measuring the real TTFs with Pillow, so a long title steps down (72→46px cream, 82→50px dark) instead of overflowing, and the description is cut at 3 (cream) or 2 (dark) lines with an ellipsis.

**CairoSVG, with the brand fonts pinned and fail-fast.** The existing PNGs were produced by CairoSVG, so rendering the template with it is what makes the acceptance criterion "typography matches the hand-made cards" hold by construction. satori (HTML/JSX → SVG, Node) would add a second toolchain and does not render our hand-made covers; resvg renders SVG better than cairo but is a Rust binary with its own font stack, and the win is not worth diverging from the existing pipeline. The three families are fetched from `google/fonts` at a **pinned commit** into the gitignored `.github/fonts/` (cached in Actions), and exposed to cairo through a private `fonts.conf` set via `FONTCONFIG_FILE` — nothing is installed system-wide, every runner renders the same bytes, and before rendering the script asks `fc-match` to prove that each family resolves to one of those files, failing the job otherwise rather than substituting a fallback. The variable TTFs work because fontconfig exposes their named instances (`Playfair Display:bold` → the Bold instance).

**Generated files are marked, so hand-made work is never overwritten.** Ownership is decided by a PNG text chunk (`Software: guibranco/blog build_og_cards.py`), not by the file name — one existing hand-made PNG is already named exactly like its post slug. A marked card is re-rendered whenever its Post changes in a PR (title or description edits stay in sync; identical output produces no commit); a same-named unmarked file blocks generation with an explicit message unless `--force` is passed. To take a card back into hand-made territory, replace the PNG (or add a `cover:` SVG) — the marker disappears with it.

**Committed, not build-time — a deliberate deviation.** ADR-0009 (proposed) planned the SVG→raster step inside the Jekyll build with nothing committed, and ADR-0011 rejected commit-based generation for gallery derivatives. This ADR narrows ADR-0009: the rasterization it anticipated happens at PR time and its output is committed, because (a) `image:` must be plain front matter that `jekyll-seo-tag`, `schema.html` and `audit_blog.py`'s existence check can read — a build-time file would need a plugin to inject it and an audit exception for a path that does not exist in the branch; (b) it is one 60–110 KB PNG per illustrated post, replacing a commit that was already being made by hand ("Add files via upload"), not the N-derivatives-per-photo growth ADR-0011 avoided; (c) the bot commits target the PR branch, not `main`, so there is no race with the deploy that a push to `main` triggers. ADR-0009's folder layout and ADR-0011's derivative pipeline are untouched.

## Consequences

- New workflow `og-cards.yml` (PR events on `_posts/**`, plus `workflow_dispatch` with a `commit` switch — an unticked manual run only uploads the PNG+SVG as an artifact, which is how to preview or re-render a card). New CI dependencies: `cairosvg`, `pyyaml`, `libcairo2`/`fontconfig` (already on `ubuntu-latest`), and a download from `raw.githubusercontent.com/google/fonts` at the pinned commit.
- Like the sync workflow's commits, the bot push uses `GITHUB_TOKEN` and does not re-trigger `blog-audit.yml`; the audit already ran on the human push, and the bot commit only adds a `.png` `image:` and its file — the exact shape the audit's raster/extension checks accept.
- `image:` stops being something an author writes for an illustrated post. `cover:` remains optional and hand-authored; when present it is what gets rasterized. New optional front matter field `card_style`.
- `.github/fonts/` is gitignored. Running the script locally needs `python3 -m pip install cairosvg Pillow pyyaml` plus a working libcairo (Linux/macOS; on Windows use `--svg-only` to inspect the template, or the manual workflow run for a real render).
- The postmortem series and every other existing post keep their hand-made cards — nothing is backfilled; a post is only touched when it appears in a PR without a raster `image:`.
- See [`CONTEXT.md`](../../CONTEXT.md)'s **Hero** term, which now names the generated-card shape alongside the illustrated and travel shapes.

## Amendment — 2026-09-23: the card follows the Post into its image folder

A Post that keeps its `cover:` SVG in its own image folder (`assets/img/posts/<folder>/cover.svg`, the shape ADR-0009 proposes) now gets its card as **`cover.png` beside that SVG**, and `image:` points there, instead of at the flat `assets/img/posts/<post-slug>.png`. Templated cards, flat covers and ownership by the `Software` marker are unchanged. Keeping the Post's assets together costs nothing for discoverability: Open Graph and Twitter scrapers only need an absolute, stable, 1200×630 URL, and for image search the URL still carries the Post's name in its folder segment (alt text, the page's own text and the JSON-LD `image` in `schema.html` matter far more than the file's basename). The one rule that follows is that a card's URL must not change after the Post has been shared, because scrapers cache it — which is why nothing existing is renamed.

Because `build_images.py` and `audit_blog.py` treat every raster inside a per-post folder as a Gallery photo (ADR-0011), both now skip `cover.*`: the Hero is not a Gallery photo and gets neither sanitizing nor derivatives. The workflow moved from Python 3.12 to 3.13 at the same time (`Path.read_text(newline=…)` had crashed the first real run); `requirements-og-cards.txt` and the shared `requirements-images.txt` carry both the cp312 and cp313 wheel hashes, so the other workflows' 3.12 runners keep resolving.
