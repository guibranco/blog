# Gallery photos get responsive AVIF/WebP derivatives generated at build time; the committed photo is sanitized in place and stays the lightbox original

Travel posts embed Galleries of phone photographs straight from the per-post image folder (`/assets/img/posts/<post-slug>/`, ADR-0009): a 4000-px JPEG of 2–3.5 MB was the `<img src>` of a thumbnail rendered at 180–250 CSS px, with no `width`/`height`, so every gallery both dominated page weight (the Amsterdã post shipped 14 MB in six thumbnails) and shifted layout while loading. Separately, those committed photos still carried EXIF GPS coordinates and the device model — while the site's Editorial Notes promise readers that photo coordinates and metadata are cleaned.

**The committed photo is the single source and it is sanitized in place.** `.github/scripts/build_images.py` rewrites a photo that still carries metadata: EXIF orientation is baked into the pixels, EXIF/XMP are stripped, the ICC profile is kept, and a JPEG is re-encoded with its own quantization tables and subsampling so the round-trip is as close to lossless as JPEG allows. The result is idempotent (a clean file is never touched) and it is the file that serves three roles at once: the `<img src>` fallback, the GLightbox full-resolution target (`href`), and the input to every derivative. `audit_blog.py` blocks a PR whose committed Gallery photo still has GPS data or an unbaked orientation, so the leak is caught before merge rather than at deploy.

**Derivatives and their manifest are build output, never committed.** The same script writes AVIF and WebP at 480/960/1600 px (never upscaling; a source narrower than 1600 px also gets a rung at its own width) into `/assets/img/derived/<post-slug>/`, named with a short hash of the source so a changed photo can never be served with a stale derivative, and writes `_data/images.json` with each photo's intrinsic post-orientation dimensions and derivative sets. `deploy.yml` runs it before `jekyll build`, with `assets/img/derived/` restored from `actions/cache` keyed on the sources, so a routine deploy re-encodes nothing and a cold cache costs roughly a second per photo per rung. The alternative — a workflow that generates and commits derivatives, in the style of `sync-category-tag-data.yml` — was rejected: every travel post would permanently add its derivatives to git history on top of its originals, bot commits on `main` would race the deploy that the same push triggers, and it would contradict ADR-0009's stance that generated rasters are `_site` artifacts, not source.

**`_includes/photo.html` is the one way to place a Gallery photo.** It keeps the GLightbox contract untouched (`a.glightbox` with `href` = original, `data-gallery`, `data-title`, the same `alt` rules) and adds what the hand-written snippet lacked: `<picture>` with AVIF and WebP `srcset`, a `sizes` default tuned to the `.photo-gallery` grid, explicit `width`/`height`, `loading="lazy"` and `decoding="async"`. When the manifest has no entry — a flat file outside a per-post folder, or a local checkout where the script has not been run — it emits the previous plain `<img>` markup, so nothing existing breaks and local `jekyll serve` never fails for lack of derivatives.

## Consequences

- New build dependency: the deploy and audit workflows install Python with `Pillow>=11.2` (the first release whose wheels bundle an AVIF encoder). No Ruby-side change; Jekyll just copies `assets/img/derived/` like any asset.
- `assets/img/derived/` and `_data/images.json` are gitignored. A fresh clone renders galleries as plain `<img>` until `python3 .github/scripts/build_images.py` is run once; the README's local-development section says so.
- Sanitizing rewrites committed binaries. The six Amsterdã photos were rewritten by this change (their previous bytes, GPS included, remain in git history — rewriting history is out of scope). From now on, a photo that lands with metadata fails the audit with the exact command to fix it.
- HEIC/HEIF sources are not supported by Pillow's wheels; convert phone originals to JPEG before adding them to the folder.
- Only per-post folders are in scope. Galleries that still use flat files (`/assets/img/posts/post-Lego-*.jpg`) and Heroes (`image:`/`cover:`, including the 16 MB Malta hero) keep their current, unoptimized markup until they are moved into the folder shape — the opportunistic migration ADR-0009 already anticipates. Extending `<picture>` to the Hero in `_layouts/post.html` is the natural follow-up.
- See [`CONTEXT.md`](../../CONTEXT.md)'s **Gallery** term, which now names the sanitized source and the build-time derivatives.
